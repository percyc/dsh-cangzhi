# ADR-003：证据入口结构化 + 工作台档位 / 全屏阅读

- 状态：已采纳
- 日期：2026-08-31

## 背景

工具结果卡片目前只对 `knowledge_search` 和 `knowledge_ask` 提供"打开来源证据/右侧预览"按钮，而 `knowledge_query_dataset` 的结果对象里其实已经带 `document_id` + `dataset_id`，却仍走 `resultPreview` 的纯文本路径，导致用户看到查询结果后无法一键跳到工作台预览，只能手工搜索。`answerEvidence` 也只靠正则从 `knowledge_ask` 的 answer 文本里识别引用，遇到模型用结构化 JSON 输出时无法可靠命中。

藏知工作台只有一个连续的 360–760 像素拖拽宽度，没有"档位"概念；阅读长 Markdown/PDF 时用户希望能在"窄/标准/宽"之间快速切换，全屏阅读又是常见的可读性诉求。

## 决策

1. 工具结果卡片统一通过 `cangzhi-open-document` 事件向工作台派发来源证据，不再依赖脆弱正则：
   - 抽出 `src/client/lib/evidence.mjs`，提供 `idNumber`、`collectStructuredEvidence`、`dedupeEvidenceLinks`、`fallbackAnswerEvidence` 四个纯函数。
   - `EvidencePreview` 解析 MCP `content` / `structuredContent` / `result` 三层后递归收集 `document_id + dataset_id` 链接。`knowledge_query_dataset` 命中即展示最多 3 条去重来源，按钮文案统一为"打开来源证据 · 右侧预览"。
   - `answerEvidence` 改为先尝试把 answer 解析为 JSON 取结构化链接，再回退到《文档名》document_id … dataset_id … 的正则匹配，保留旧行为。
2. 工作台加入 `narrow / standard / wide` 三档（420/520/720）和全屏阅读切换：
   - 抽出 `src/client/lib/workbench-size.mjs`，提供 `clampWorkbenchWidth`、`detectWorkbenchSize`、各 `readWorkbench*FromStorage` 等纯函数。
   - 顶栏新增档位按钮组（`▮ / ▮▮ / ▮▮▮`）和全屏按钮（`⤢ / ⤡`），分别写入 `cangzhi-workbench-size` 与 `cangzhi-workbench-fullscreen`。外层 frame 同时挂 `[data-cangzhi-workbench-fullscreen='true']`，CSS 把右侧留白扩到 `min(1100px, 100vw - 32px)`。
   - 原有拖拽继续生效，endResize 时按 360–760 收尾并推断档位，写入 `cangzhi-workbench-size` 兼容旧值。
   - 移动端（max-width 760px）媒体查询同步隐藏档位按钮与拖拽手柄，保留 DSH 已有折叠行为，不引入新回归。

## 取舍

- 优点：证据入口覆盖到所有带结构化引用的工具，正则仅在 JSON 拿不到时兜底；用户能在一指之内切换工作台密度与全屏阅读。
- 代价：`lib/client.js` 体积增加约 11KB（gzip 后 +3KB）；`cangzhi-workbench-size` / `cangzhi-workbench-fullscreen` 仅存浏览器 localStorage，未来如要跨设备同步需要接入 DSH 设置体系。
- 旧 `cangzhi-workbench-width` 仍然有效，被 `readWorkbenchWidthFromStorage` 在缺失 size/fullscreen 时按宽度推断档位，避免历史用户丢失偏好。

## 后续

- `tests/workbench-and-evidence.test.mjs` 覆盖档位表、storage fallback、证据收集与去重、文本回退、idNumber 边界。
- 若 DSH 之后提供 `settingsScope` 用于工作台偏好，再把档位/全屏迁到 DSH 设置面板（参考 ADR-001 后续段）。
